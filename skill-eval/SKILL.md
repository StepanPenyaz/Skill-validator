# Purpose

`skill-eval` answers five questions about a target skill:

1. Does `SKILL.md` follow `references/preferred-structure.md`? (structure check; blocking findings stop the evaluation)
2. Do its sections mean what they should, and is it safe? (rubric review)
3. Does it do its job on real inputs, and what does that cost? (repeated runs on several models, one `claude -p` process per input)
4. How close is each produced output to the verified output, and how stable is it between repeats? (comparison and similarity)
5. Which model should run the skill? (recommendation from similarity, stability, tokens, time and cost)

It writes two reports: a short `final_report.md` (summary, skill name and description, model recommendation) and a `detailed_final_report.md` with everything.

It can also compare two versions of one skill.

Every step that needs Claude's judgement runs in its own subagent with a clean context. The model runs are `claude -p` processes started by a script. The main session organises the work and copies numbers. It never judges the target skill itself.

# When to Use

- The user wants a full evaluation of a skill, or a cost and behaviour measurement.
- The user wants V1 and V2 of a skill compared.
- The skill has no example inputs and verified outputs yet. This skill creates them (and says they need review).

# When NOT to Use

- The user only wants the structure check. Tell them to run `/skill-static-review <skill_dir>`. It needs no Claude session.
- The user wants the skill written or fixed. This skill only evaluates.

# Workflow

Work in the target skill's own folder, `<skill>/`. Files go here:

```
<skill>/
├── step_reports/   01_structure.md, 02_rubric.md, 04_comparison_<model>_a.md and _b.md, 05_similarity.md
├── static_report/  latest output of /skill-static-review
├── evals/
│   ├── inputs/
│   ├── verified-outputs/
│   ├── GENERATED.md       only when the eval data was generated by a subagent
│   └── <skill>_<version>_outputs/
│       ├── <model>/run_<r>/<input>        produced output
│       ├── <model>/run_<r>/<input>.json   status, tokens, real cost, time, turns, tools
│       ├── <model>/run_<r>/<input>.jsonl  full transcript
│       └── run_on_<model>_report.md       measured numbers
├── final_report.md            short report
└── detailed_final_report.md   full report
```

Save each step's report before you start the next step.

## Step 0: Pick the mode

- **New skill:** one skill directory. Run steps 1 to 6 once.
- **Two versions, V1 already has `detailed_final_report.md`:** run steps 1 to 6 for V2. Pass V1's directory to step 6 as `--baseline`.
- **Two versions, V1 has no `detailed_final_report.md`:** first run steps 1 to 6 for V1 in its own clean subagent. Then run steps 1 to 6 for V2 in a separate clean subagent. Then do step 6 for V2 with V1 as `--baseline`.

A "clean subagent" for a whole version run means: start a subagent that gets only the path of that version and this skill's instructions, not this conversation.

## Step 1: Structure check (gate)

1. Run:

   ```bash
   python skill-eval/scripts/generate_static_report.py <skill_dir> --out <skill_dir>/static_report/static_report.md --fail-on-blocker
   ```

   It is the same report `/skill-static-review` writes. Exit code 2 means the report has Blocker findings.
2. Copy the report into `step_reports/01_structure.md`.
3. Choose the profile by what the skill produces (`references/profiles.md`). `document` is the default and fits skills that turn a text task into a structured Markdown result. If the skill works with something else (code, images, data files) and no implemented profile fits, stop and tell the user which profile is missing; do not use `document` for it. Give the same `--profile <name>` to steps 4 and 5, and say which profile was used when you report.
4. **If the exit code is 2, stop.** Do not run steps 2 to 5. Go to step 6: the reports will say the evaluation stopped at the structure check and list only the blocking findings. Warnings and info-level findings never stop the run. Report them and keep going.

## Step 2: Rubric review

1. Read `rubric_review` in `config.yaml` for the model and the token limit.
2. Start one subagent on that model. Give it the skill folder path, `references/rubric.md`, and the token limit. Ask it to answer:
   - Do the sections of `SKILL.md` follow their intended meaning?
   - Are there security risks in the skill?
3. Ask it to confirm every finding against the real text before reporting it.
4. Save its answer as `step_reports/02_rubric.md`.

## Step 3: Evaluation data

1. If `evals/inputs/` and `evals/verified-outputs/` both exist, are not empty, and every input has a verified output with the same file name, go to step 4.
2. If a folder is missing or empty, start a generator subagent. Give it only the skill's name, description and `references/eval-data-authoring.md`. It writes `evals/inputs/` and `evals/verified-outputs/`. Do not wait for the user.
3. Write `evals/GENERATED.md` listing the files the subagent created, and say that they need review. The reports then carry a note that the data was generated.
4. If both folders exist but some file names have no partner, stop and tell the user which files have none.

## Step 4: Run the target skill

Run the script. It starts one `claude -p` process per model, run and input, in a clean temporary project that holds the skill but not `evals/`:

```bash
python skill-eval/scripts/run_skill.py <skill_dir> [--models opus,sonnet] [--runs X] [--jobs N] [--profile <name>]
```

The models are `default_models` of `config.yaml`, plus any models the user asked for (`--models`). The number of repeats X is `runs_per_model` there. A case that fails (error, timeout, budget, empty output) is recorded as failed and the rest go on. The script writes the outputs, the `.json` and `.jsonl` files, and `run_on_<model>_report.md` (tokens, time and cost are means per full run, as reported by `claude -p`; see `references/token-capture.md`). If the command cannot run (for example `claude` is not logged in), the cases fail and the reports say `unavailable`. Never fill in numbers by hand.

## Step 5: Comparison and similarity

1. Run the similarity script first:

   ```bash
   python skill-eval/scripts/compute_similarity.py <skill_dir> [--profile <name>]
   ```

   It writes `step_reports/05_similarity.md`: score, run spread, stability and median run per model, a table per run and per case, the flags, and the facts it did not find. A case without output scores 0 and makes its run incomplete.
2. For each model start **two** fresh subagents (judge a and judge b), independent of each other. Give each one `evals/verified-outputs/` and the produced outputs of that model's median run (column `Median run`). Judge a writes `step_reports/04_comparison_<model>_a.md`, judge b `..._b.md`, containing table rows, one per verified output:

   ```
   | 01-api-order-cancel.md | <input file> | <model> | <version> | <what matches, what is missing> |
   ```

   The note must be specific, for example "does not contain the required test cases". After the rows, each judge writes one last line:

   ```
   Verdict: <Equivalent | Minor gaps | Major gaps> - <one sentence>
   ```

   `Major gaps` means a requirement of the verified output is missing or contradicted. `Minor gaps` means differences in wording, detail or extra content only. `Equivalent` means the same requirements. This is the only place where the content is judged. A model is dropped from the recommendation only if both judges say `Major gaps`. If they disagree the verdict is `Disputed` and a person must check it.

## Step 6: Reports

Run:

```bash
python skill-eval/scripts/build_final_report.py <skill_dir> [--baseline <older_skill_dir>]
```

It writes two files.

`final_report.md` contains only:

1. Summary (what was evaluated, the recommended model, the note that the eval data was generated, or that the run stopped at the structure check)
2. Skill name
3. Skill description
4. Model recommendation (table of similarity, verdict, stability, tokens, time and cost per model, the recommended model, and why)
5. Blocking structure findings, only when the structure check found Blockers: just those findings

`detailed_final_report.md` has numbered sections: 1 Summary (with three charts when two versions are compared), 2 Skill name, 3 Skill description, 4 Run results, 5 Output comparison (notes and similarity per case), 6 Skill structure check, 7 Skill rubric review, 8 Model recommendation (same as section 4 of the short report), 9 Run stability and behaviour.

The recommendation is computed by a fixed rule, not by a model: drop models with too few complete runs, unstable results between repeats, or a `Major gaps` verdict from both judges; take the models within the run-to-run noise (at least `recommendation.tolerance_points`) of the best similarity; recommend the cheapest of them. If `step_reports/05_similarity.md` is missing, the section says so.

When `--baseline` is used, the tables show V1, V2 and the change.

Tell the user where `final_report.md` is, which model is recommended and why, whether the eval data was generated, and the top-line findings.

# Rules

- Use a separate subagent, with a clean context, for the generator, the rubric review, every judge, and any V1 baseline run. This keeps the target skill from being judged with knowledge from the main session. Model runs are separate `claude -p` processes started by `run_skill.py`.
- Blocker findings of the structure check stop the evaluation. Warnings and info never do.
- Cost, tokens and time must be measured values. If one is missing, write `unavailable`.
- Do not produce `.json` reports. All reports are Markdown. The `.json` files beside the produced outputs are raw run records, not reports.
- Do not give the skill a numeric score. The similarity number scores a produced output against its verified output, never the skill. Notes must say what is right or wrong.
- The model recommendation is only what the rule in step 6 produces. Do not override it by hand. If the user wants a different trade-off, change `recommendation.tolerance_points` for this run and say so.
- Generated eval data must be marked in `evals/GENERATED.md` so the reports can say it needs review.

# Decision Guidelines

- More models than the default: add them for this run only (`--models`). Do not edit `config.yaml` unless the user asks.
- More or fewer repeats: pass `--runs` for this run. A single run cannot show instability, so the report marks the model `single run`.
- The rubric review runs out of tokens: report which rubric categories were not covered. Do not raise the limit yourself.
- A model run fails: the script records the failure and goes on. Do not retry by hand unless the user asks; a model with too few complete runs is reported as `insufficient`.
- Unstable results on two or more models point at the skill (check the transcripts); on one model they point at that model. Say which.

# References

- `references/preferred-structure.md`: the structure `SKILL.md` is checked against.
- `references/rubric.md`: the rubric for step 2.
- `config.yaml`: all settings: models, repeats, runner limits, stability limits, recommendation tolerance, rubric review model and token limit, similarity profiles, severity of each static check.
- `references/profiles.md`: profiles, one per kind of skill (data, run, collection, evaluation), and how to add one.
- `scripts/profiles/__init__.py`: the profile contract and the loader. `scripts/profiles/document.py`: the `document` profile.
- `references/eval-data-authoring.md`: how to write (or generate) `evals/inputs/` and `evals/verified-outputs/`.
- `references/token-capture.md`: where tokens, time and cost come from.
- `scripts/structural_check.py`, `scripts/generate_static_report.py`: the static review and the gate.
- `scripts/run_skill.py`: the model runs.
- `scripts/compute_similarity.py`: similarity, stability and flags.
- `scripts/build_final_report.py`: builds both reports, including the model recommendation.
